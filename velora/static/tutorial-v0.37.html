1. How the decision is made

Identify the active user and roles.
The session is established by the request authentication scope.
Expand active role inheritance.
Only active roles from the current company database contribute inherited grants.
Check explicit RBAC policy.
If the company configured a decision for this DocType and operation, that decision is authoritative. Any explicit deny wins.
Use metadata permissions as the compatibility baseline.
When no RBAC decision exists for that DocType/operation, existing DocType metadata permissions continue to apply.

2. Configure role policy

Use the v0.36 company-local administration service to create a role and grant its permissions. This release wires those grants into runtime enforcement.

from velora.controlplane.role_admin import RoleAdministration
from velora import db

roles = RoleAdministration(db.get_engine())
roles.create_role(company_admin, "Accounts Clerk")
roles.set_permission(
    company_admin, "Accounts Clerk", "Sales Invoice", "read", True
)
roles.set_permission(
    company_admin, "Accounts Clerk", "Sales Invoice", "submit", False
)
roles.set_field_access(
    company_admin, "Accounts Clerk", "Customer", "tax_id", "hidden"
)

The actor passed to the administration service must be a company administrator or have the System Manager role.

3. What field restrictions mean

Editable

The user may read and update the field, subject to DocType permissions.

Read only

The value can be returned, but a change through document persistence is rejected.

Hidden

The field is omitted from serialized documents and default list columns. Explicit selection and filtering are rejected.

Security note: hiding a field in a browser is not authorization. Velora applies these checks on the server. Custom app endpoints must use the framework's guarded serializer and query helpers.

5. Current boundaries

  • Configurable row-level predicates are not included yet.
  • Specialized report/custom SQL endpoints still require an authorization audit.
  • Graphical role administration and dedicated role-management APIs remain future work.
  • Background-job actor/service-principal permissions need a dedicated design.

Knowledge check

If a role inherits “read allowed” but has an explicit “read denied” grant for the same DocType, what happens?

Access is denied. An explicit deny wins over an inherited allow.
